# v0.2.1 小红书候选版真机验收

本清单由用户执行。账号数据验收只操作小红书 `com.xingin.xhs`，不安装 Fixture、不操作微信。开发端可以覆盖安装候选包并只读核对版本，但不代替用户执行恢复，也不在验收完成前创建 GitHub Release。

## 1. 安装前基线

1. 保存当前可回退的同签名 Manager APK 和 KernelSU 模块 ZIP。
2. 记录候选提交 SHA、APK/ZIP SHA-256、Manager 证书 SHA-256、现有 Aggregate、活动账号、账号名称和重启启动开关。
3. 确定后续用于保护现场的 Base、待测分账号和完整备份保存位置；这些文件在 0.2.1 成对安装后、任何恢复测试前创建。
4. 不卸载小红书、不清除数据，不直接修改 CE/DE 或 UClone 槽目录。

## 2. 成对升级与基本回归

1. 覆盖安装同签名 0.2.1 Manager，安装 0.2.1 KernelSU 模块并重启、解锁 user0。
2. 首页必须显示 Manager/Runtime `0.2.1`，原 Aggregate、账号名称、活动账号和重启开关保持不变。
3. 执行 `Base → 分账号 → Base`；每次切换并启动小红书，登录状态和账号数据必须对应目标空间。
4. 0.2.1 Manager 配旧模块或旧 Manager 配 0.2.1 模块时必须只显示版本不匹配，不得修改账号。
5. 分别创建当前 Base、待测分账号和全部账号的加密保护备份；复制到第二个可靠位置并确认都能进入恢复预览，之后才能开始覆盖恢复测试。

## 3. 备份范围和运行行为

1. 单独备份一个非活动分账号：正在使用的小红书不应被停止，文件可进入预览，预览只显示该分账号。
2. 单独备份当前账号：小红书在备份窗口保持停止且不能被重新拉起；完成后恢复原账号和启用状态，但 App 保持停止，由用户手动打开。
3. 单独备份 Base：预览只显示“系统原始空间”。
4. 备份全部账号：预览同时显示 Base 和全部分账号，账号名称、活动账号、重启启动开关、来源版本/系统/设备正确。
5. 默认加密备份必须要求密码；错误密码显示认证失败，正确密码进入预览。明确关闭密码后可生成未加密备份，并显示风险提示。
6. 多进程 App 切换时允许主进程、push 进程和 App Zygote 延迟退出，但只有目标 UID 全部进程归零后才能改变 CE/DE 视图；确认窗结束仍有进程时必须保持原账号并失败。微信的同类历史日志只作为该通用修复的证据，本轮不操作微信账号。
7. 取消保存、不可写 SAF 位置或存储不足时不得出现可被当作成功备份的文件，原账号和运行状态必须恢复。

## 4. 单账号恢复

1. 将一个分账号备份恢复为新分账号：新账号使用归档名称，原有 Base 和其他分账号不变，恢复后的账号可正常启动登录。
2. 将同一备份覆盖一个现有非活动分账号：确认页明确显示覆盖，目标内容变为备份账号，未选择账号不变。
3. 分账号映射中不得出现 Base 目标；两个归档账号不得选择同一个现有目标。
4. 将 Base 单账号备份恢复到 Base：Base 目标固定且不可改；确认后当前 Base 被完整覆盖，所有现有分账号仍保留。
5. 恢复成功后核对账号名称、活动高亮、重启启动设置和小红书真实登录状态。

## 5. 完整恢复

1. 在测试前记录一个“额外分账号”，该账号不在待恢复的完整备份中。
2. 对完整备份设置映射：Base 固定覆盖 Base，一个分账号覆盖现有目标，另一个分账号恢复为新账号。
3. 输入确认词并恢复。结果页必须逐账号显示成功、失败或未处理。
4. 成功后 Base 和所有已选择账号内容与归档一致；额外分账号保持存在且数据不变。
5. 归档活动账号恢复成功时，它成为当前账号；若该账号失败，则保持恢复前活动账号。归档的重启启动设置只在对应活动账号成功时恢复。
6. 最终 App 启动失败时，不得回滚已经恢复的账号；小红书应保持停止，用户可稍后手动启动。

## 6. 文件与失败路径

1. 截断备份副本或修改其中字节：预览或恢复必须报告文件无效，不能提交任何账号。
2. 错误密码、取消选择文件、包名不存在、签名信息不可读取时不得创建临时配置或改动现有账号。
3. 当前安装签名与归档不匹配时必须显示显著警告，并要求输入完整包名；不能使用普通“覆盖”确认绕过。
4. 在第一个账号成功、后续账号失败的受控场景中，结果必须区分成功/失败/未处理；已成功账号保留，未提交账号不被覆盖。
5. Runtime 离线、版本不匹配或 account-I/O busy 时操作停止，不得绕过 Runtime 直接写 Base/槽目录。
6. Base 回滚副本空间不足时，必须在停止 App 或修改 Base 前返回“存储空间不足”；目标 Base、恢复暂存、当前账号和 intent 均保持不变，释放空间后可以重试。

## 7. 中断恢复

这一节会故意中断事务，只在第 2 节的三个保护备份均可预览后执行。

1. 在备份涉及 Base/当前账号时重启设备；解锁后 Runtime 应恢复原活动账号和 App 原启用状态，但不自动启动小红书。
2. 在恢复解包阶段重启：正式 Base/槽不得出现半个 CE/DE；暂存被清理，原账号保持。
3. 在某账号提交期间重启：该账号要么成对回滚，要么成对保留为已提交状态，不能出现 CE/DE 混合；之前已成功账号继续保留。
4. 开机恢复完成后普通切换仍可用，`list_account_io_status` 为空，维护挂载和本次 transfer/rollback 目录已清理。
5. 另做一次非重启中断：备份/恢复前台 Service 被系统终止后，备份页只读显示残留 App、操作类型和阶段；未确认时不得自动中止，二次确认后恢复原账号视图并清空状态。

## 8. 结束状态与发布

1. 根据第 1 节记录恢复用户希望保留的 Base/活动账号和重启启动开关；不要删除测试中需要保留的备份文件。
2. 核对 APK、ZIP 和 `SHA256SUMS.txt` 来自同一提交 SHA。
3. 只有全部必测项通过且用户明确确认“可以发布”后，才创建 GitHub Release。失败时停止测试，保留现场；只在没有活动 account-I/O intent 时覆盖回退 0.1.9 Manager/模块并重启。

## 通过条件

- Base 可以作为独立账号备份并被恢复覆盖；完整恢复必定包含并处理 Base。
- 备份只覆盖账号 CE/DE 范围，密码、文件损坏和路径攻击均 fail-closed。
- 恢复按账号成对提交，部分成功可解释、可保留，中断后能够自动收敛。
- 0.1.9 的创建、切换、重命名、删除、重绑、开机恢复和源目录隔离无回归。
